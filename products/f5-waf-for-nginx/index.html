F5 WAF for NGINX

A web application firewall that runs inside the NGINX data plane you already operate, rather than in front of it. There is no extra hop and no second proxy to scale — policy is enforced at the same point that already terminates and routes the request. Formerly NGINX App Protect WAF.

Three version numbers, and they are not the same

The standalone product is at 5.14. NGINX Ingress Controller v5.5.4 pins 5.13.4, and NGINX Gateway Fabric 2.6.7 pins 5.13.2. When checking whether a feature is available to you, the number that matters is the one pinned into your data plane, not the standalone release.

How it attaches

This is the part most likely to trip you up: the integration is genuinely different on each data plane, and the mental model does not carry over.

On NGINX Ingress Controller

Runs in process, as a module compiled into a purpose-built NGINX Plus image — the debian-image-nap-plus build target and its variants. Policies are defined as APPolicy resources, with APLogConf for security logging and APUserSig for custom signatures.

You attach a policy to a VirtualServer through NIC’s own Policy CRD, using its waf block, or to a plain Ingress through app-protect annotations.

On NGINX Gateway Fabric

Runs out of process, as two sidecars injected into each NGINX pod: waf-enforcer applies policy to incoming traffic and waf-config-mgr distributes bundles. It needs its own image; the standard nginx-plus image has no WAF module.

A WAFPolicy attaches through Gateway API inherited policy attachment. A route-scoped policy overrides a Gateway-scoped one rather than merging with it, and only one may target a resource at a given level.

NGF does not compile policies. It fetches a pre-compiled bundle from NGINX Instance Manager, the NGINX One Console, or an HTTP URL.
