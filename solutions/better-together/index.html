Better Together

F5’s Kubernetes products are usually described one at a time, which makes it hard to tell which ones are meant to be combined and which are alternatives. This page is the answer to that, and it is explicit about provenance: each combination is marked either as something F5 documents, with the guide and version matrix to prove it, or as guidance — architecturally sound, but without an F5 document behind it.

Documented — F5 publishes a guide Guidance — sound, but no F5 document

Why the distinction matters

A combination marked Guidance is not a warning. It means the building blocks are documented but the specific pairing is not, so you will not find a step-by-step guide or a tested version matrix for it. Treat those as designs to validate in your own environment rather than recipes to follow.

Documented integrations

F5 publishes a guide for each of these, and in most cases a version matrix too.

BIG-IP + Container Ingress Services + NGINX Ingress Controller

L4 and TLS at the edge · L7 inside the cluster

Documented

This is F5’s documented two-tier design, and the one to reach for if you want an appliance tier in front of an in-cluster tier. A BIG-IP at the cluster edge load-balances across the NGINX Ingress Controller pods; CIS watches those pods and reprograms the BIG-IP pool as they change. NGINX then owns per-application L7 routing inside the cluster.

The link between the tiers is an IngressLink custom resource, which carries the virtual server address (or an IPAM label) and a selector matching the NGINX Ingress Controller service labels. CIS must run in CRD mode, and the BIG-IP virtual server needs a Proxy Protocol iRule so the original client address survives the first hop.

Two details worth knowing before you commit: this path requires NGINX Plus Ingress Controller, not the OSS build, and F5 documents that CIS does not update the ingress address in the Ingress status.

F5 WAF for NGINX + NGINX Ingress Controller

WAF enforced in process, in the ingress data plane

Documented

The WAF compiles into NGINX Ingress Controller as a module, using a purpose-built NGINX Plus image. You define an APPolicy resource and attach it either through NIC’s own Policy CRD for a VirtualServer, or through app-protect annotations on a plain Ingress.

Because it runs in process there is no additional hop and nothing extra to scale — but it does mean the WAF version is whichever one is pinned into your controller release, not the latest standalone release.

F5 WAF for NGINX + NGINX Gateway Fabric

WAF enforced out of process, alongside each data plane pod

Documented

On Gateway Fabric the same product works quite differently. Enabling it injects two sidecars into each NGINX pod — waf-enforcer and waf-config-mgr — and policy attaches through a WAFPolicy using Gateway API inherited policy attachment.

Policies are compiled outside the cluster and fetched as bundles from NGINX Instance Manager, the NGINX One Console, or a URL. A route-scoped policy overrides a Gateway-scoped one rather than merging with it, and a second policy targeting the same resource at the same level is rejected as conflicted.

NGINX Gateway Fabric + Gateway API Inference Extension

Model-aware routing to self-hosted models

Documented

Round-robin is the wrong load-balancing algorithm for inference: requests are long-lived, expensive, and their cost varies enormously. The Gateway API Inference Extension replaces it with an Endpoint Picker that NGINX Gateway Fabric consults per request, giving routing by queue depth, adapter and serving priority.

An InferencePool becomes an HTTPRoute backend reference. One caveat F5 documents and worth repeating: the Endpoint Picker is third-party software, and traffic between NGF and it uses TLS with certificate verification disabled by default.

Container Ingress Services across several clusters

One BIG-IP virtual server, many clusters

Documented

CIS can expose applications spread across several Kubernetes or OpenShift clusters behind a single BIG-IP virtual server, in either a standalone or an HA topology. Pool members are node ports and the cluster mode uses static routes rather than tunnels.

It needs an extended ConfigMap, the --multi-cluster-mode flag, a local cluster name, and read-only kubeconfig access to each cluster. Note that Service type LoadBalancer is unsupported in the active-active and ratio HA modes.

BIG-IP fronting NGINX Ingress Controller without IngressLink

L4 at the edge · L7 inside the cluster

Guidance

If IngressLink is more coupling than you want, CIS also supports Service type LoadBalancer with a load balancer class, which will allocate a BIG-IP virtual server for any Service — including the NGINX Ingress Controller Service. The result is the same two tiers with a looser join between them.

Both halves are documented separately. What is not documented is this specific pairing: there is no F5 walkthrough for "front NGINX Ingress Controller with a BIG-IP using Service type LoadBalancer", so you are assembling it from two guides rather than following one. In exchange you are not restricted to NGINX Plus, as IngressLink is.

NGINX Ingress Controller and NGINX Gateway Fabric in one cluster

Ingress API and Gateway API, side by side

Guidance

The two controllers watch disjoint resource types — NIC takes Ingress and its own CRDs, NGF takes Gateway API — and NGF maps each Gateway to a dedicated data plane deployment. That makes per-application cutover practical: run both, scope NIC by IngressClass, and move one workload at a time instead of scheduling a cluster-wide migration.

F5 documents running multiple controllers with IngressClass scoping, and documents the Ingress-to-Gateway conversion. It does not publish coexistence as a topic in its own right, so treat the combination as a pattern rather than a supported configuration with a tested matrix.

BIG-IP Next for Kubernetes with NGINX Ingress Controller or Gateway Fabric

Cluster gateway · per-application L7

Guidance

It is tempting to describe this as "BNK for L4, NGINX for L7", and that framing is wrong twice over. BIG-IP Next for Kubernetes is documented as an L4–L7 product, not an L4 one, and F5 publishes no reference architecture pairing it with either NGINX data plane. If you have seen that pairing asserted, it was not from an F5 document.

What is defensible: BNK consolidates ingress, egress, firewall and DDoS at the cluster boundary and is where NetOps teams extend existing control into Kubernetes; the NGINX data planes are where platform and application teams own per-application L7 routing through Ingress or Gateway API. Those are different operating models, and F5’s own solutions page frames them as complementary options chosen by who operates the cluster — not as tiers of one stack.

Layering them is a reasonable design. It is your design to validate, not one you can point at a guide for. The documented two-tier path is IngressLink, which uses classic BIG-IP and CIS.

Choosing between them

Platform teams own the cluster

Start with NGINX Ingress Controller or NGINX Gateway Fabric. Both are open source, configured entirely through Kubernetes resources, and need no appliance. Add F5 WAF for NGINX when you need enforcement in the data plane.

NetOps already runs BIG-IP

Container Ingress Services turns the BIG-IP you operate into the cluster’s ingress tier without changing who owns it. Add IngressLink if you also want an NGINX tier inside the cluster.

Egress, telco or AI infrastructure

BIG-IP Next for Kubernetes is the only option here that controls egress as well as ingress, carries telco signalling protocols, and offloads onto BlueField-3 DPUs.

Leaving the community controller

The migration tool if you are staying on Ingress, ingress2gateway if you are moving to Gateway API. You can do both, one application at a time.
